Ask Mode

Read-only. Answers questions. Never touches files.

"What does this service do?"
"Explain this RxJS operator"
"How does auth work in this project?"

How it works

Copilot reads your codebase and answers questions. No file changes, no side effects. Safe to use anytime.

Why it's helpful

Fastest way to understand unfamiliar code. Use it before making changes — build a mental model first, then act.

Plan Mode

Think first, act second. Review the strategy before any code changes.

"Add pagination to the user list"

→ Step 1: Add pageSize param to UserService
→ Step 2: Update UserList component with paginator
→ Step 3: Add route query params for page state
→ Step 4: Write unit tests for pagination logic
→ Step 5: Update e2e test

[Approve] [Edit plan] [Cancel]

How it works

Copilot generates a structured plan. You review, edit, or cancel before any code is written. Then it implements exactly what you approved.

Why it's helpful

You stay in control of the approach. Catch wrong assumptions early — before they become 8 files of wrong code to undo.

Agent Mode

How it works

Agent drives end-to-end. Reads code, makes changes, runs terminal commands, fixes test failures — all autonomously in one session.

Why it's helpful

Maximum speed for well-defined tasks. But also most opaque — no visibility into decisions, no audit trail, no boundaries. Can we do better?

Three triage modes

  • Query — read-only, instant answer
  • Quick fix — single-file, engineer + verifier
  • Workflow — multi-file, full pipeline

Self-correcting loop

  • Verifier fails → coordinator re-routes
  • Minor fix → back to engineer
  • Plan wrong → back to planner
  • 3 retries max → human escalation

Triage: Query

Read-only. @angular answers directly. No sub-agents needed.

@angular "What version of Angular is this app using?"

→ Reads package.json
→ "Angular 18.2.0, with Nx 19.8, TypeScript 5.5"

Instant answer. No planner, no engineer, no verifier. The coordinator recognizes this is a question and handles it directly.

Triage: Quick Fix

Single file, clear intent. Engineer + Verifier only.

@angular "Add trackBy to this @for loop"

→ Engineer edits dashboard.component.html
→ Verifier runs build + lint
→ Done. 1 file changed.

Skips the planner — the "plan" is obvious. Engineer makes the change, verifier confirms it compiles and passes lint.

Triage: Workflow

Multi-file, structural, or ambiguous. Full pipeline.

@angular "Add a loading spinner to the dashboard"

→ Planner: scans dashboard, identifies 3 API calls,
  recommends HDS LoadingIndicator, plans 4 file changes
→ Engineer: implements across component, service, template, test
→ Verifier: build pass, 12/12 tests pass, no lint warnings

Full pipeline. If verifier fails, feedback loops back. If engineer realizes scope is bigger, it self-escalates to coordinator for re-planning.

Event-Driven Execution

Workflows are declarative YAML. The relay publishes events, dispatches phases, monitors progress.

# .orch/workflows/angular-migration.yaml
phases:
  - name: Standalone migration
    agent: engineer
    skill: /angular-migrate-standalone
    pre-check:
      skill: /angular-scan-arch
      args: --counts-only
      capture: before-patterns
    post-check:
      skill: /angular-scan-arch
      args: --counts-only
      capture: after-patterns
    checkpoint: true
    verify: true
    on-failure: rollback-to-checkpoint
    collect: [files-changed, pattern-delta, duration]

Each phase declares: which agent runs it, pre/post checks for deltas, whether to checkpoint and verify, what to collect for the report, and what to do on failure.

Why Not Request-Response?

The typical agent loop breaks at scale. Event-driven execution solves it.

Request-Response (typical)

  • Context bloats: 30K+ tokens by phase 5
  • User types "continue" 10 times
  • No parallelism — one tool at a time
  • Crash = start over — no state persistence
  • Tools run out (25–100 per turn)

Event-Driven (ORCH)

  • Fresh context per phase (~2K tokens)
  • Scripts run automatically (zero tokens)
  • Parallel scan phases (4x faster)
  • Crash-resilient — file-based state
  • Full tool budget per AI phase

In a 10-phase migration, request-response burns ~300K tokens with degrading quality. Event-driven uses ~20K total with consistent quality per phase.

Version-Aware Stack Resolution

Right docs for the right version. Automatically.

  • Auto-detects Angular version from package.json at session start
  • Loads version-appropriate reference docs and patterns — v16 projects get NgModule/constructor patterns, v19+ get signals/standalone
  • ~50% token savings from loading only relevant docs instead of the full v16–v21 corpus
  • Cascading fallback: cache → detect → pin → default
  • Zero config required — works out of the box, with optional .orch/config.yaml version pin override

Governance & Safety

Two-layer enforcement. What makes ORCH enterprise-ready, not just a developer tool.

Two-layer enforcement

  • VS Code settings.json (HARD): terminal commands allowlist, file edit patterns, autopilot limits
  • ORCH boundaries.yaml (SOFT + hooks): per-agent tool restrictions, file scope, blocked commands
  • Audit trail: every tool call, file edit, token logged to .orch/runs/

What's enforced

LayerExampleEnforcement
VS Code settingsrm: false in terminal.autoApprovePlatform blocks it
ORCH hooksPlanner tries edit tool → preToolUse hook exits 1Hook blocks it
ORCH boundariesEngineer writes outside src/ → postToolUse logs violationLogged + scored

Hard boundaries cannot be bypassed. Soft boundaries are logged and scored. Instructions rely on LLM compliance — but hooks catch violations.

Create a Custom Workflow

Declarative YAML that chains skills into a multi-phase pipeline.

# .orch/workflows/springboot-migration.yaml
name: springboot-migration
trigger: "upgrade|migrate spring boot"
report:
  title: "Spring Boot {{from}} → {{to}} Upgrade"

phases:
  - name: Scan dependencies
    agent: planner
    skill: /springboot-scan-deps
    collect: [before-versions]

  - name: Upgrade Spring Boot
    agent: engineer
    skill: /springboot-migrate-version
    pre-check:
      skill: /springboot-scan-arch
      capture: before-patterns
    post-check:
      skill: /springboot-scan-arch
      capture: after-patterns
    checkpoint: true
    verify: true
    on-failure: rollback-to-checkpoint

  - name: Final verification
    agent: verifier
    skills: [/springboot-test, /springboot-review]
    on-failure: report-as-partial

The coordinator reads this YAML and executes phase by phase. Status bar shows progress. Report stitched automatically.

  • Audit trail schema

  • Boundary enforcement

  • IDE integration hooks
